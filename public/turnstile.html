Cloudflare 学习站第 10 课 · Turnstile

有表单，不等于只有人在提交。

Turnstile 帮程序识别自动化滥用请求。
它提供验证依据，是否继续处理，由你的后台程序决定。

01 · 实际问题

公开留言变成了垃圾信息入口。

网站允许访客留言。正常人偶尔提交一次，机器人可以直接调用后台接口，连续提交大量无用内容。运营要清理垃圾，数据库和程序也在为它们工作。

只在网页上禁用按钮没用：机器人可以跳过网页。Turnstile 改善的是“接受请求前的判断”：让后台要求一张可核验的临时凭证，再决定是否继续。

什么时候不需要？纯阅读的静态页面通常不必加；可信的程序之间调用，也应使用适合程序的身份认证。需要防止访客入口被自动滥用时，再考虑它。

02 · 三个核心概念

检查、凭证、后台核验。

网页组件：发起检查的小部件
Cloudflare 在访客浏览器里运行检查，很多时候不用人做题；有时需要交互。它不是你的表单处理程序。
验证凭证：一次性的“检查结果单”
程序里常叫 token。有效期是 5 分钟，只能核验一次。它不是密码，也不表示这个访客是谁。
服务端核验：后台确认这张单子真实有效
Worker 向 Cloudflare 查询凭证，核对它是否来自本站、是否用于这个提交入口。网页上的绿色勾号不能替代这一步。

与前课的区别：R2 保存文件；D1 保存并查询记录；Turnstile 为接受一次请求提供依据，不负责保存文件或留言。它也不替代登录、输入校验、提交频率限制和人工内容审核。

03 · 运行逻辑与分工

凭证交给谁，谁作决定？

  1. 1 · 访客与网页完成检查
    内容 + 凭证交给 Worker
  2. 2 · Worker先校验输入
    向 Cloudflare 核验凭证
  3. 3 · Cloudflare返回是否有效
    以及来源与用途
  4. 4 · Worker 决定通过才处理
    失败则拒绝

这里 Cloudflare 的“核验凭证”服务常叫 Siteverify。Worker 的核验请求只发送凭证与后台密钥，不发送留言正文。本课收到的留言只作回显，未写入 D1、KV 或 R2；凭证也不存进这些资源。

第一次提交
网页取得凭证，Worker 请求核验。通过后才运行处理留言的代码；Cloudflare 不会自动帮你保存留言。
再次提交、改文字、等待过久
本例每次提交后重新获取凭证。改文字也要做普通输入校验；复用已经核验的凭证或等待超过 5 分钟，会被拒绝，需要重新验证。网络失败时也先拒绝，不当作通过。

开发者做一次：创建组件、登记网站域名、把后台密钥放进 Worker 的秘密设置，并把“核验通过才处理”的代码接进提交入口。

程序每次做：取凭证 → 随表单提交 → 后台核验 → 处理或拒绝。不会要求运营逐张管理凭证。

用户或运营决定：用户填写什么；运营决定哪些入口需要防护、通过后做什么、哪些内容仍需审核。

需要动手时再看：资源归属、代码、配置与免费范围

组件属于 Cloudflare 账号，可用于多个登记的网站。同一个组件能共用，但每个后台仍要核对自己的来源域名与用途，不能只凭“验证成功”接受别的入口的凭证。

sitekey 是放在网页上的公开组件编号；secret 是只留在后台的核验密钥。本课通过已授权的 Cloudflare 插件直接存入 Worker 的秘密设置，密钥不进入网页或 GitHub。

网页：内容 + token → POST /api/turnstile/submit
Worker：secret + token → Cloudflare Siteverify
只有 success 为真，且 hostname/action 符合预期，才继续处理。

本例用途名是 lesson_submit；生产后台只接受 lab.aecai.us.ci 与本站 workers.dev 备用域名，不把 localhost 放进生产来源名单。组件登记允许本地开发，但本地后台应有独立设置和测试标识。

Cloudflare 管理凭证的生成、验证和有效期；你的程序管理业务内容的保存、更新、删除。删除或重配组件属于账号管理操作，不等于删除 D1 中的留言。

Turnstile Free：最多 20 个组件，每个最多 10 个主机名，挑战与验证请求不限次数；Worker 本身仍有自己的运行额度。无需先开通 R2 或付费 Workers。

浏览器需允许组件脚本和框架访问 challenges.cloudflare.com；组件加载失败时页面会说明情况。详细代码在仓库，不必先记命令才能理解这课。
